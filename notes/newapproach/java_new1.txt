Heap:
- String Pool is there inside this
- There is no order of allocation inside heap
- GC is used to delete the unreferenced objects in the heap

Heap = Young Generation + Old Generation
Young Generation = Eden + Survivor space
Survivor space = s0 + s1

- Whenever an object is created it is first stored in young generation, now it might happen some are unreferenced and some are referenced
- After a certain time GC will run, it will see whoever is unreferenced, it will delete those, now whoever is referenced will be moved to either s0 or s1 (Mark and Sweeep Algorithm)
- Next time again some new objects might be created and stored in young generation, again when GC will happen, same process will be followed, along with that whoever is stored in s0 will be moved to s1 and vice versa (alternate every time)
- Now when objects are moving between s0 and s1, it's age increase every time, once it reaches a threshold it is "promoted" means, it is moved to old generation area

Important - Whenever GC is run in young generation, it is called as Minor GC and whenever it is running in new generation it is called Major GC

Metaspace (Perm Gen / Method Area)
- It stores static variables (also called class variables)
- It stores class metadata
- Use native memory, does not use Java Heap Memory

Old Generation is also called "Tenured Generation"

-- When Metaspace was known by the name "Perm Gen", it was part of heap memory, so it was not expandable, but now after becoming Metaspace, it is a separate entity outside of heap which uses native memory so it is expandable as per requirements

+------------------------+
|      Types of GC       |
+------------------------+

1. Serial GC
- It uses a single thread to perform GC, when this happens, all application threads are paused, once GC is done, application resumes. This is also called Stop-The-World (STW)

2. Parallel GC
- It is same as Serial GC, but it uses multiple threads so work is completed faster and STW time is reduced

3. Concurrent Mark-Sweep GC
- It tries level best to work concurrently with the application threads, so it minimizes the STW time and in best case, it will not cause STW. Here defragmentation does not happen, so free space can be in fragments

4. G1 (garbage first) GC
- It is similar to concurrent mark sweep gc, but it defragments the free space as well. Also, it has some concurrent improvements, so it is the default GC algorithm since java 9.

Till Java 8 (inclusive) - Parallel
From Java 9 onwards - G1

How float is stored in Java?
It uses 32 bit IEEE 754 standard

sign bit - 1 bit
exponent - 8 bit
mantissa/significant - 23 bit

Convert float number to machine representation-
step 1 - convert the number to binary number
step 2 - convert to 1.___  x  2^(u)
step 3 - add bias to exponent (float bias is 127)
step 4 - write binary in form of sign bit, exponent and mantissa

remember that, 1.____, here ____ is called mantissa

To convert back in reverse fashion-
[(-1)^(sign bit)] x [(1 + mantissa)] x [2 ^ (exponent - 127)]

|      Singleton Design Pattern      |
+------------------------------------+

We already know how to write normal singleton design pattern using eager initialization and lazy initialization.

In two phase locking, there is a problem, there may be multiple cores, we know that each core is having its own cache, so generally whatever variable you might be using to hold the object will also exist in the respective cache, now what if someone asks for the object in other cache, then it will again show NULL which will result in creation of an object once more. So, whatever static variable we have created for holding the object should be declared as "volatile". Marking it as volatile means it will not rely on cache, all read/write operations will happen directly on memory level.

Bill Pugh Solution of Singleton Design Pattern - There is another solution which is faster than two phase locking and also ensures thread safety.

class Singleton {

    private Singleton() {
        System.out.println("Object created");
    }

    private static class SingletonHelper {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return SingletonHelper.INSTANCE;
    }
}

In Java, inner classes are not loaded when outer classes are loaded at the start of the program, it is only loaded on demand when someone refers it. Also the initialization of a class in java is thread safe and the guarantee is given by JVM internal working itself.

There is another way of achieving this using ENUM, enum initialization is also thread safe guaranteed by JVM, constructor is automatically private.

enum Singleton {
    INSTANCE;
}

Initially, there is a interface Map<K,V>, in this interface there is a nested interface Entry<K,V> which, if some class implements has to implement getKey(), getValue() etc methods

So Map<K,V> Interface has size(), isEmpty(), containsKey() etc
Entry<K,V> has getKey(), getValue() etc

Now HashMap<K,V> is one of the class which implements Map<K,V>, so hashmap has to provide implementation for size(), isEmpty() etc. Now, in hashmap, we have a nested static class Node<K,V> which implements the Map.Entry<K,V> interface so it has to provide the implementation of getKey(), getValue() etc

Also, in class HashMap<K,V> there is a entry Node<K,V>[] table, which create a array of Node

by the way, class Node looks like this,
class Node:
	final int hash;
	final K key;
	V value;
	Node<K,V> next;
	
We already know the implementation of hashmap, so I will only write some important things which should get special attention

HashMap Implementation follows a contract between equals() and hashCode()
1. If two objects are equal according to equals(), they MUST have the same hashCode()
2. If two objects have the same hashCode, they don't necessarily have to be equal.

Initial settings of hashmap,
DEFAULT_INITIAL_CAPACITY = 1 << 4; (2 power 4 is 16)
DEFAULT_LOAD_FACTOR = 0.75f
TREEIFY_THRESHOLD = 8;

Now, when size of hashmap reaches 0.75 (75%) of initial capacity, then the capacity increases to (2 power 5 = 32) and this process continues, Thus, we understood what is initial capacity and load factor

Now, we already know that at every array index we are maintaining a linked list, when this linked list size becomes greater than or equal to TREEIFY_THRESHOLD, then the linked list gets converted to balanced binary search tree (Red Black Tree)

Thread safe(HashMap) = ConcurrentHashMap or HashTable

==> LINKED HASH MAP

It is a kind of hash map, but it has two special features, it can maintain either
1. Insertion Order
2. Access Order (Acces the most recently used ones)

Internal implementation is same as hash map, but it uses doubly linked list, In class LinkedHashMap we have a nested class Entry<K,V> extends HashMap.Node<K,V>, so we have those 4 fields in hashmap plus before and after pointer, so, it means, whenever a new node is inserted, the value is stored in the after pointer, thus maintaining insertion order

Now, when initializing LinkedHashMap we can use the constructor LinkedHashMap(int initialCapacity, float loadFactor, boolean accessOrder), if we give accessOrder as true, we can have a "Access Order" LinkedHashMap

LinkedHashMap is not a thread safe collection and there is no thread-safe version available as well. To get a thread safe version of it, we will use the Collections utility class and create a object by this syntax,

+--------------------------+
|      MULTITHREADING      |
+--------------------------+

Whenever a program is made to run, it will be assigned a JVM instance which will have some part of heap space. Now, let's say you want to customize how much heap size to be given, then you can do it at the start of the program by using this command

java -Xms256m -Xmx2g className

There are various terms in JVM instance which is created

1. Code Segment - It contains the compiled bytecode (machine code) of the program, It is shared among threads, it is in read only mode

2. Data Segment - It contains global and static variables, threads can modify these variables so synchronization is required

3. Heap - It is common for all threads, whenever we use the "new" keyword, objects are stored here, threads can read and modify heap data so again proper synchronization is required

4. Stack - Each thread is having its own stack, which is used to manage method calls, local variables etc

5. Register - Each thread is having its own register, when JIT converts bytecode into machine code, it uses registers to optimize the machine code, It also helps in context switching

6. Counter - Stores the address of the instruction which is to be executed

Thread Lifecycle
New, Runnable, Waiting, Blocked, Timed Waiting, Terminated

New - A thread that has not yet started is in this state.
Runnable - A thread executing in the Java virtual machine is in this state.
Blocked - A thread that is blocked waiting for a monitor lock is in this state.
Waiting - A thread that is waiting indefinitely for another thread to perform a particular action is in this state.
Timed Waiting - A thread that is waiting for another thread to perform an action for up to a specified waiting time is in this state.
Terminated - A thread that has exited is in this state.

Now, let's see some points
Blocked - Suppose a thread was working and suddenly some I/O operation is there, so it will go to blocked state, now when it goes to blocked state, it will release all monitor locks

Waiting - wait() is called, it will resume when notify() is called again, it will release all monitor locks

Timed Waiting - sleep() or join() called, so it will wait for some time, it will NOT release all monitor locks

There's a question, what is monitor lock?
When you use the synchronized keyword on any method, it will acquire a lock on the object by which it was called, now even though some other method will be called, they cannot acquire a lock if they are using the same instance of the class, because every class has one monitor lock

wait() - It stops execution and waits until other thread notifies it
notify() - wake up any one thread which was waiting
notifyAll() - wake up all threads which are waiting for this monitor's lock

only wait() releases the lock
notify() and notifyAll() does not releases lock, just alerts everyone that once the method ends, lock is going to be available

Why stop, resume and suspended method is deprecated?
stop - terminates the thread abruptly without releasing the lock, no resource clean up happens
suspend - it does the same work as wait(), but does not release the lock
resume - it is used to resume the thread which is suspended with suspend method, since suspend is deprecated, resume is also deprecated

Till now, we have only seen monitor locks, and we know that, monitor lock acquires lock on object, so different objects working are not dependent on each other

But, let's say there is a scenario where there is a critical section, and no matter multiple objects are there but we want only one thread should access it, then we need some other kind of locks

We have some other kind of locks as well which are,
1. Reentrant Lock

In this, instead of objects, the lock depends on the lock object created by us, we will first create a object of reentrant lock and pass this lock, with this object, we can call the .lock() and .unlock() method

2. ReadWriteLock

In this, we have two types of lock, Shared Lock and Exclusive Lock, whenever we want to do read operation we can acquire the shared lock and else we can acquire the exclusive lock, Now what is the matrix of possibilities of shared-exclusive lock is quite simple and covered in CSE engineering

By the way, ReadWriteLock is an interface, and ReentrantReadWriteLock is a concrete implementation so we have,
ReadWriteLock lock = new ReentrantReadWriteLock();

again this lock is also not dependent on objects, rather everyone shares this lock

3. Stamped Lock

Before starting, understand this,
Locks are of two types, Pessimistic Locking and Optimistic Locking

Pessimistic locking means to acquire a lock, do some work in critical section and then release the lock, whereas optimistic locking means to read the object and note its state, now do some operation and when you are going to commit, first check whether the state of the object matches the state which you stored earlier, If YES then commit, else rollback because some other process has modified the value in between, again you can start from beginning

Stamped Lock supports both ReadWriteLock functionality as well as Optimistic locking functionality. You can refer internet for methods available for both of them, It's quite simple and looks like ReadWriteLock

4. Semaphore

In semaphore, the only difference is that we can send multiple threads in critical section. We can do this by creating a semaphore object and giving the number of threads in the constructor.

Now, we already know about wait() and notify(), these are used in inter-thread communication when the locks are acquired by synchronized keyword, i.e "monitor locks"

But, what if we are not acquiring the monitor locks, what if we are dealing with custom locks that we saw just now, so in such scenario we have similar methods like await() and signal() which are replacement of wait() and notify()

==> Atomic (Lock free)

Suppose we want to achieve concurrency, so we have two methods of doing so,
1. Locks, that we have already studied
2. Atomic Integer, Atomic Boolean etc

CAS (compare and swap) - this is a low level operation which directly involves CPU, in this, we first read a value, then we compare it with the expected value, and then if it is same then only we update it

In Atomic Integer, CAS is used

Now there is a problem in CAS as well, suppose thread reads x=10, now before the next step executes, some thread comes and performs x=12, then x=10 again, now thread 1 will think nothing changed, but in reality it went to 12 and came back to 10, this is called as ABA problem, this problem can be easily resolved by maintaining versions or timestamps

==> Thread Pool

It is a group of threads which are pre-created so that whenever some tasks comes, we can re use these threads instead of creating and destroying threads every time

Advantages
1. Thread creation time can be saved (allocation of stack, PC etc)
2. Overhead of managing the threads can be saved
3. If more number of threads are there, then context switch will happen again and again, which will waste time, because in the process of context switch, CPU will be idle. Maintaining a thread pool can limit excess number of threads

==> Future

In executor interface, we have a method execute(), which we use in ThreadPoolExecutor as well to send the task. Now this execute method actually returns a Future<?> object

This future object can return us the status of the work that is going on by the thread. It has several methods like .isDone(), .cancel() etc, which is used to examine the status of the task

.get() is used to make the calling thread wait, until the task is completed by the working thread, while .get(time, unit) is used to check the status after the specified time

Now, we already know execute() method, there is another method known as submit() which comes in three flavours,
1. submit(Runnable) -> It will not return anything
2. submit(Runnable, Data structure) -> it cannot return anything but can do changes in the data structure provided
3. submit(callable) -> it can return any value and future will hold that

==> Completable Future

It is a child of future, so it provides all functionalities + chaining of other tasks as well. To get a completable future back we use a static method in class CompletableFuture, which is CompletableFuture.supplyAsync(()->{}) which accepts a supplier. It will perform some work and give back the output in async manner

We have two more methods, .thenApply() and .thenApplyAsync(), it is used to do some operation on the result of previous task, .thenApply() is a synchronous operation which will be done on the same thread which did the previous task where as .thenApplyAsync() creates a new thread and does the work in async fashion

Also, remember that if you have multiple .thenApplyAsync(), there is no guarantee on the order of execution of the tasks

In such scenarios, if we want the result of previous async operation to be used in the next one, we use .thenCompose, it will work in async manner but the thread will be same as previous, Also it flatten the result in to a single CompletableFuture object rather than nested object in the case of .thenApply() versions

.thenComposeAsync() also make sure that the result of previous operation will be used in next operation, but it also does it in some other thread

Again, we have a method .thenAccept which will accept a consumer and do something

We also have .thenCombine method which can combine results of two completable futures

==> Executors

It is a utility class in java.util.concurrent package which allows us to create various types of thread pools

i. Fixed Thread Pool

ExecutorService obj = Executors.newFixedThreadPool(number of threads)

In this we have a fixed number of threads, Also, threads will not get destroyed even though it is kept idle. This should only be used if we know how much workload will be there in prior state

ii. Cached Thread Pool

ExecutorService obj = Executors.newCachedThreadPool()

In this, we can create INT_MAX number of threads, depending on number of tasks that come, If any thread is not being used for 60 seconds, it will get destroyed. It is good for handling short lived tasks, but if alot of huge tasks come, it is dangerous

iii. Single Thread Executor

ExecutorService obj = Executors.newSingleThreadExecutor()

In this, only a single thread is there, and it will be alive even if idle, queue will be maintained, to be used when we need to process the tasks sequentially, Obviously there is no concurrency

iv. Work Stealing Pool Executor

It is used to create fork-join pool, It is a kind of pool which creates some threads which we mention / equal to available threads. These threads are used to perform recursive tasks

Working of fork-join pool
1. In this we maintain a submission queue where tasks are allocated, if any thread is idle they will pick up the task and proceed with it
2. In this architecture, each thread maintains a separate queue as well, "work stealing queue", whenever the thread does a recursive action, it proceeds with the first branch of recursion and it stores the other branches in to its work stealing queue
3. Now, whenever a thread becomes idle, it will first check the submission queue, if there is no task available there as well, then this thread will steal the task from other thread's work stealing queue
4. Remember one thing, each thread picks the task from front and steals the task from the back of other thread's queue
5. submit() stores the task in submission queue, fork() stores the task in the work stealing queue

ForkJoinPool obj = ForkJoinPool.commonPool();
Future<Integer> ans = obj.submit(new ComputeSum(0,100));

class ComputeSum extends RecursiveTask<Integer> {}

In ComputeSum class, we will write the recursive code and call fork() for all sub tasks, and join() to get the result of those tasks

.shutdown() - initiate orderly shutdown of executor service, it will not accept any new task but if some task have already started they will continue

.awaitTermination() - this method takes in some time, and waits till that time, if the executor task is completed in that time interval then it will return true else false

.shutdownNow() - it will put the best effort to shutdown the executor service and interrupt the ongoing task as well

If you make a thread pool of this kind, then you can call the .schedule() and start tasks at some fixed delay or intervals etc

==> Virtual Thread (java 19 onwards)

Till now whatever threads we have seen are known as "platform threads" which means, when a thread is created, it makes a system call and creates a thread at OS-level, there is a direct mapping between java thread and OS thread

Now, we have a idea of virtual thread, which can be used, if let's say there are 2 processors, then also you can make 10 virtual threads, out of those threads, whoever wants to run a task can connect to one of OS threads and perform the task, Now let's say if some thread wants to do some I/O operation etc, then it can disconnect from the OS-thread and mean while other thread will connect and proceed

Virtual thread creation time is very less, as compared to create lot of OS threads
