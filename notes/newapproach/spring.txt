Build Lifecycle:
1. validate
2. compile
3. test (unit test)
4. package (.jar)
5. verify
6. install to local repo
7. deploy

1. validate phase [mvn validate] - in general maven does not stop us from writing any style of code but suppose you want to enform some style then you can write xml code inside <build> tag, plugins are already available on internet, so you can use that to do the required stuff

2. compile [mvn compile] - It compiles all java code and creates a target folder which holds all .class files

3. test [mvn test] - It will run the test cases that you wrote inside test package

4. package [mvn package] - It will create a .JAR file for the compiled classes

5. verify [mvn verify] - bydefault there is no verify tasks, but we can add a plugin in <build> task which will do some verification task, example - there are some plugins which removed unused variables, empty catch block etc

6. install [mvn install] - It will install the .JAR package into our local repository in .m2/repository folder

If you want to change the location of installation in .m2 folder, you can change that in settings.xml which is present in .m2 folder

7. deploy [mvn deploy] - It means to deploy .JAR file to remote repository, for company purpose, they will give xml snippet which you have to put in <project> which will deploy it to company repository.

We know that a bean can be created by @Component or @Bean. @Component can create a bean if we have a default constructor, If we have a parameterized constructor then who will provide the values for constructor? So, our application will fail to start.

In such scenario we can use @Bean annotation, we can keep a simple POJO, create a separate configuration class with @Configuration annotation and create a method with @Bean annotation which will return a object with parameterized constructor called.

In a system beans are created in two ways with respect to timeline - Eager and Lazy

Eager beans are created at the time of application start up while Lazy beans are created when they are needed in code.

Singleton beans are created eager where as prototype beans are created lazy by default. If we want to make a singleton bean lazy, we can use @Lazy annotation.

|     DEPENDENCY INJECTION     |
+------------------------------+

When a class needs the power of another class, we can give it via the IOC container, and this process is called dependency injection

Now what are the ways of doing it?
public class User:
    Order order = new Order();

This is the most easiest way to do it, but the problem is tightly coupled, suppose because of our project requirements we want to make Order as interface with some child classes, so now we have to change the User class as well due to the presence of "new Order()"

Second problem is, according to "D" of solid principle, we should not depend on concrete class, instead we should always work with interfaces

Field Injection Problems:
1. We cannot make our field final, if we try to make it we will get a compile time error, Now what we can do is make it null at the beginning, even after that reflection can now reassign it which breaks the final keyword rule

2. Suppose somewhere in some other file, someone did User obj = new User(); (no one is stopping us from doing this), and then they called obj.methodName(); and let's say this method is using order obj method, so it can throw NPE

Setter Injection Problems:
- we cannot make the variable as final because spring can inject dependency using reflection by using setter

Constructor Injection:
Spring version 4.3 ---> If only one constructor is present, no need of autowired as well

People often ask, is there a problem in constructor dependency? There is indeed one, if there are too many parameters, then imagine how your constructor will look

(arg1, arg2, arg3, ... , argN) something like this, so actually it's not a disadvantage because it is giving us a hint that we should refactor our code since, this class is dependent on so many resources

Circular Dependency
- Use @Lazy annotation on top of @Autowired, so it will not create the object at the start, so one of the class can be created at the start, this breaks circular dependency

- Suppose there are two classes, Order and Invoice, so in Invoice class, we can create a variable of order type without @Autowired or constructor, now when order class is invoked, it can create an object of type invoice without any problem, once order is created we can use @PostConstruct and set "this" to Invoice class

Unsatisfied Dependency problem
- Suppose we have a class Invoice, and we there's a dependency of Order order, now Order is a interface, so while initialization, which concrete implementation of Order to choose, for this you can use @Primary annotation of one of the concrete classes, Another approach is to using @Qualifier annotation and give a name, so you can use the same @Qualifier annotation while autowiring

@Scope(singleton)
Only one object is created per IOC, this object will be eager by default

@Scope(prototype)
Every time when it is called, a new object will be created

@Scope(request)
New object will only be created per HTTP call

Now, understand a scenario, what if a prototype class tries to create a scope request bean, so it will not be created until it is required because both are lazy in nature

But, what if a singleton bean tries at startup? It will give us "Failed to start the application" because @Singleton wants all dependencies at start, and the other class has request scope, so it is lazy by default.

To make it work we have to use a setting in @Scope(value="request", proxyMode=ScopedProxyMode.TARGET_CLASS), so at startup, it will create a dummy object and give it to the singleton class, and when a real HTTP request will come, it will replace it with the real object

@Scope(session)
It will create a new bean for every new session, obviously it is used in systems where session is maintained, so the bean will get destroyed in the /logout api, where session gets closed

@Scope(application)
If we want to maintain a single bean copy in multiple IOC containers in a huge application, then we can use this

+-----------------------------------+
|    ASPECT ORIENTED PROGRAMMING    |
+-----------------------------------+

In simple terms, AOP is the process to intercept any running method and do some task, the specified task can be performed before, after or around the method

It is used for tasks such as logging, transaction management etc which is repetitive code in multiple methods

dependency has to be added in pom.xml which is spring-boot-starter-aop

A simple AOP code will look like,

@Component
@Aspect
public class LoggingAspect {
	@Before(POINTCUT) {
		// ADVICE
	}
}

You can create a separate class where in you can write the code which will be called while intercepting any method, POINTCUT is an expression which tells spring which method should get intercepted, ADVICE is the piece of code that should be run when interception happens

Types of Pointcut:
1. @Before("execution(public String {fully qualified path}.{methodName}())")

You can use "*" which means anything
You can use ".." which means 0 or more

2. @Before("within({fully qualified path})") --> It will run for all methods in this path

3. @Before("@within({fully qualified path})") --> It will match any class having this annotation

4. @Before("@annotation({fully qualified path})") --> It will match any method with this annotation

5. @Before("args(String,int)") --> matches any method with particular arguments, If the data type is a class you can write the fully qualified class name as well

6. @Before("@args({fully qualified path of annotation})") --> matches arguments whose class is annotated with the annotation

7. @Before("target(fully qualified path)") --> matches any method which is invoked using the object of this class / interface

POINTCUT can be combined by using AND, OR condition

==> Named Pointcuts

@Pointcut("pointcut definition here")
public void myPointcut() {}

@Before("myPointcut()")
public void beforeMethod () {
	// code
}

Advice --> block of code which is executed when some pointcut matches is called advice

We have already seen @Before, @After is self explanatory, now let's see @Around,

@Around(pointcut expression)
public void aroundMethod(ProceedingJointPoint joinPoint) throws Exception {
	// do something before method invocation
	joinPoint.proceed();
	// do something after method invocation
}

An object of ProceedingJointPoint is given to us which holds the control of invocation of method, so we can place it in our method according to our need

Internal Working of AOP:

Who is parsing the pointcut expression --> PointcutParser.java

If any class is eligible for aspect, it will create a proxy, either JDK dynamic proxy or CGLib proxy, it is done by AbstractAutoProxyCreator.java

If class implements an interface --> JDK proxy is used, otherwise CGLIB proxy is used

+---------------------+
|    TRANSACTIONS     |
+---------------------+

@Transactional provides ACID properties, Internally there is an pointcut which matches all transactional annotation and whenever such method is invoked, it will call an advice, which will,
1. open a transaction
2. proceed with our method
3. if something goes wrong, it will rollback, else it will commit

All this is already written in TransactionalInterceptor class and the advice method name is invokeWithinTransaction

==> Hierarchy of Transaction Managers

<<interface>>
TransactionManager

<<interface>>
PlatformTransactionManager -- getTransaction(), commit(), rollback()

<<abstract class>>
AbstractPlatformTransactionManager -- default implementation of PlatformTransactionManager

<<concrete class>>
DataSource Transaction Manager, Hibernate Transaction Manager, JPA Transaction Manager, JTA Transaction Manager

Now, whenever we use @Transactional annotation, it will choose the appropriate transaction manager according to configuration setup in application properties or AppConfig java

Heads Up - In java app config, we have to create two method, one should return DataSource which holds config details, other should return one object of PlatformTransactionManager, many are interfaces, so return appropriate concrete classes wherever required

We can write transactions in two ways
- Declarative ==> directly writing @Transactional
- Programmatic ==>

1. we can create a method and call getTransaction(), commit(), rollback() using instance of PlatformTransactionManager
2. By using an instance of TransactionTemplate and calling it's execute method

==> Propagation

There is a question, if one transaction is happening and another method is called, that method2() will open a separate transaction or continue in this transaction itself? Question to this answer, will be given here, It all depends on the value of propagation

@Transactional(propagation = Propagation.REQUIRED)

Propagation.REQUIRED --> if parent txn is present use that, else create new
Propagation.REQUIRED_NEW --> always create a txn for this method separately
Propagation.SUPPORTS --> if parent txn is present use that, else proceed without txn
Propagation.NOT_SUPPORTED --> pause the txn, because this method want to run without txn
Propagation.MANDATORY --> use parent txn, if not there throw error
Propagation.NEVER --> if parent has txn throw ex, else continue

Again this can be used in two ways, declarative and programmatic

Declarative - Using the annotation

Programmatic - in getTransaction constructor you have to pass a object of DefaultTransactionDefinition, which can hold propagation options

==> Isolation

It tells us how the changes made by one transaction impacts other transaction

Dirty Read Problem - It T1 does some txn but does not commit, T2 came and saw the result and committed, afterwards T1 did rollback, such problem is called dirty read problem

Non Repeatable Read Problem - If we query for a row multiple times, it will give different values

Phantom Read Problem - If we did a range query multiple times and we got different number of rows

Isolation Level

READ UNCOMMITTED - high concurrency (nothing solved)
READ COMMITTED - dirty read solved
REPEATABLE READ - dirty read + repeatable read solved
SERIALIZABLE - low concurrency (all problems solved)

default isolation level is READ COMMITTED, but it depends on database as well

Types of lock acquired by isolation level,

READ UNCOMMITTED - no locks acquired
READ COMMITTED - read lock release after read, write lock holds till end of txn
REPEATABLE READ - read lock till end of txn, write lock till end of txn
SERIALIZABLE - read lock till end of txn, write lock till end of txn, range based locking, no new rows cannot be inserted in between

|    ASYNC     |
+--------------+

In java we already saw thread pool and its working, in a similar fashion we can achieve that in spring boot applications as well using @Async

In our main class, we have to annotate it with @SpringBootApplication and @EnableAsync, this @EnableAsync annotation is used because spring has to create some extra classes for enablement of async features

Once we did that, we can now mark any method with @Async annotation, so whenever this method will be called, it will run on a separate thread

Now, there is a famous question, whether @Async annotation always creates a new thread for running a method?

The answer depends, whether you are providing the configuration or not, If we did not give any configuration then it will choose "Simple Async Task Executor" which creates a new thread always

Now, how to give our own configuration?
In AppConfig Java, we have to create a bean of type "Executor", concrete class will be ThreadPoolTaskExecutor, we can do all the configurations in this and then it will be chosen as the default one

It is also allowed to give the Executor bean name in @Async annotation to specify which thread pool to use, for example @Async("myThreadPoolExecutor")

We should note one thing here, ThreadPoolTaskExecutor is a class specifically present in spring boot framework, In java we saw the ThreadPoolExecutor class was there

If in your spring boot application, you try to create ThreadPoolExecutor then even though you use @Async annotation, it will choose the SimpleAsyncTaskExecutor, to make the Java ThreadPoolExecutor as default you have to specify its name in @Async annotation

If you want that no matter what happens, you own-created Thread Pool should be used then you can make your AppConfig implements AsyncConfigurer, then no matter what happens, the thread pool configuration you created will be selected

Conditions for Async to work properly :-

1. If the calling method and the called method are within the same class, then the proxy mechanism is skipped because by default internal method calls are not intercepted by AOP in spring

2. Method annotated with @Async must be public in nature, because AOP only works on public method

Async and Transaction Management :-

- If some method1() is txn in nature, and it calls a async method2(), then method2() is not related to txn, it will be a normal method

- If some method1() is txn in nature, and it calls a async + txn method2(), so method2() will run in an independent txn, no matter what propagation is written in method1(), which means propagation does not propagate if method2() is async in nature

Good practice --> call async method, and inside async method call a simple txn method

Whenever you want to return a response from @Async method, you can make the return type as either Future or CompletableFuture, and while returning you can return new AsyncResult<>(value); and we can handle it from where it was called by using the methods of future or completable future

Now let's talk about exception handling in @Async methods,

Whenever the main threads calls @Async method, it will continue in new thread, if let's say some exception happened, so how can we handle that now,

- we can use the try catch block inside the async method

- we can create a class which implements AsyncUncaughtExceptionHandler, which needs to implement a method handleUncaughtException(), and you can write your custom handling logic here, Also, you need to make your AppConfig implements AsyncConfigurer and return an instance of AsyncUncaughtExceptionHandler

If you don't handle it, spring boot will handle it with the default SimpleAsyncUncaughtExceptionHandler class

Interceptors are similar to what we saw in AOP, whenever a method is called, if we want to do something before, after or around that method, we can do it via interceptors

Now how to create a interceptor?

1. We can create a class MyInterceptor implements HandlerInterceptor which has to give definition for preHandle(), postHandle() and afterCompletion(), Also in our AppConfig we have to do implements WebMvcConfigurer, so we again have to implement a method addInterceptors and add the interceptor and paths, once we did this, any request falling on that path will be intercepted

2. We can create our own annotation and mention it in pointcut with @annotation targeting our own annotation

What is difference between postHandle() and afterCompletion() ?
postHandle() will run if preHandle() is successful, but afterCompletion() will run even if its success as well as in the case of exception

==> Filters vs. Interceptors

Filter is a layer which is before servlets, whereas interceptors work after servlets and before controller invocation

We can use a filter when we want to perform some generic action which is common for all the servlets, like spring security things etc whereas interceptors are used when we want to perform some specific action inside the selected servlet

If there are multiple filters in filter layer, or multiple interceptors in interceptor layer then we can order them as well

We already know how to create interceptors, now let's see how to create a filter :-

We can make a class and make it child of Filter, now we can define three methods init(), doFilter(), destroy(), In these three, doFilter handles the business logic, You can continue the filter chain by calling filterChain.doFilter(), by calling this, the next filter will start running

Again, we have to register the filters in AppConfig

+------------------------------------------+
|    EXCEPTION HANDLING IN SPRING BOOT     |
+------------------------------------------+

When we are returning response entity, we can add the response in the manner of .status().headers().body(), we can keep the body at last because it returns a response entity, but others return a body builder object

Status Code:
202 Accepted - Request is successful, work has started in back end, maybe some batch processing or schedular etc

304 Not Modified - Used for caching, it frontend ask some resource, we give it along with the last modified time, now again when frontend asks that same resource, we check in DB whether it was modified since then or not, if not we can give back 304 not modified

429 Too Many Requests - When we have a rule of 10 requests in 1 minute, but we got 11th request

If you create a @ExceptionHandler in controller and one in Global Exception Handler class, the one which is there in controller gets more priority

In spring boot, any exception that will happen will be handled by these classes in order, if anyone handles it will not move forward,
1. ExceptionHandlerExceptionResolve --> Controller Advice, Exception Handler
2. ResponseStatusExceptionResolver --> @ResponseStatus
3. DefaultHandlerExceptionResolver

If you don't handle the exception and it is thrown at run time, so some one from above will handle and give some default response, but if we want full control, we should handle it and send back Response Entity

If NPE or some custom exception is thrown, then no resolver can handle that, so it goes to "Default Error Attributes" where default things are set

We can caught uncaught exception with @ResponseStatus annotation

If the situation is as follows,
@ExceptionHandler
@ResponseStatus
method()

then exception handler will not work, so whatever we returned will not be shown, instead spring will take control and pass whatever is given in Response Status annotation

|    SPRING DATA JPA     |
+------------------------+

Instead of traditional JDBC we should use JdbcTemplate, It reduces all the boiler plate code so we only have to call methods and send parameters to do any specific CRUD operations, Also in traditional JDBC, if any exception comes, it will always give "SQLException" which is very abstract in nature, whereas if we use JdbcTemplate, it gives granular level of exception like DuplicateKeyException, QueryTimeoutException etc

HikariCP is a connection pool management library, if hikaricp is not there then we have to create connection to DB, do our task and close the connection everytime, but now hikari does all those things by creating reusable connections

In spring data jpa, because of our application properties configuration EntityManagerFactory object is created during application startup, for each application property database, there is one EntityManagerFactory, this class acts as a factory to create entity managers

In application properties, we have to specify the value of transaction type as either RESOURCE_LOCAL or JTA, first one is responsible for managing transactions for a specific db, but the latter one can handle transactions across multiple DBs

EntityManager is an interface which provides methods like persist(), merge() etc to perform CRUD operations on entities, Internally when we use JPA save() etc, these either directly call entity manager methods or perform some additional coding with entity manager methods

If JPA is internally calling entity manager methods, then why we are not using entity manager directly?

We can use entity manager in this fashion,

@PersistenceContext  --> @Autowired + some additional settings
EntityManager entityManager

then we can use it like entityManager.save(obj), Now it will give error because internally entityManager rejects insert, update and delete queries if they are not in a transaction, but when we use JPA method save(), internally it calls persist() along with @Transactional annotation

Life cycle of an entity

New (transient) -> persist() -> Managed (persist) -> flust() -> DB

Managed -> detach / close entityManager -> Detached

DB -> get() -> store in L1 -> give back to user

Managed -> remove() -> removed in L1 -> flust() -> remove in DB

Detached -> merge() -> Managed
