+---------------+
|     MAVEN     |
+---------------+

- uses POM xml file, and gives build generation, documentation and dependency resolution

Build Lifecycle:
1. validate
2. compile
3. test (unit test)
4. package (.jar)
5. verify
6. install to local repo
7. deploy

1. validate phase [mvn validate] - in general maven does not stop us from writing any style of code but suppose you want to enform some style then you can write xml code inside <build> tag, plugins are already available on internet, so you can use that to do the required stuff

2. compile [mvn compile] - It compiles all java code and creates a target folder which holds all .class files

3. test [mvn test] - It will run the test cases that you wrote inside test package

4. package [mvn package] - It will create a .JAR file for the compiled classes

5. verify [mvn verify] - bydefault there is no verify tasks, but we can add a plugin in <build> task which will do some verification task, example - there are some plugins which removed unused variables, empty catch block etc

6. install [mvn install] - It will install the .JAR package into our local repository in .m2/repository folder

If you want to change the location of installation in .m2 folder, you can change that in settings.xml which is present in .m2 folder

7. deploy [mvn deploy] - It means to deploy .JAR file to remote repository, for company purpose, they will give xml snippet which you have to put in <project> which will deploy it to company repository.

+---------------+
|     BEANS     |
+---------------+

We know that a bean can be created by @Component or @Bean. @Component can create a bean if we have a default constructor, If we have a parameterized constructor then who will provide the values for constructor? So, our application will fail to start.

In such scenario we can use @Bean annotation, we can keep a simple POJO, create a separate configuration class with @Configuration annotation and create a method with @Bean annotation which will return a object with parameterized constructor called.

In a system beans are created in two ways with respect to timeline - Eager and Lazy

Eager beans are created at the time of application start up while Lazy beans are created when they are needed in code.

Singleton beans are created eager where as prototype beans are created lazy by default. If we want to make a singleton bean lazy, we can use @Lazy annotation.

+------------------------------+
|     DEPENDENCY INJECTION     |
+------------------------------+

When a class needs the power of another class, we can give it via the IOC container, and this process is called dependency injection

Now what are the ways of doing it?
public class User:
    Order order = new Order();

This is the most easiest way to do it, but the problem is tightly coupled, suppose because of our project requirements we want to make Order as interface with some child classes, so now we have to change the User class as well due to the presence of "new Order()"

Second problem is, according to "D" of solid principle, we should not depend on concrete class, instead we should always work with interfaces

Field Injection Problems:
1. We cannot make our field final, if we try to make it we will get a compile time error, Now what we can do is make it null at the beginning, even after that reflection can now reassign it which breaks the final keyword rule

2. Suppose somewhere in some other file, someone did User obj = new User(); (no one is stopping us from doing this), and then they called obj.methodName(); and let's say this method is using order obj method, so it can throw NPE

Setter Injection Problems:
- we cannot make the variable as final because spring can inject dependency using reflection by using setter

Constructor Injection:
Spring version 4.3 ---> If only one constructor is present, no need of autowired as well

People often ask, is there a problem in constructor dependency? There is indeed one, if there are too many parameters, then imagine how your constructor will look

(arg1, arg2, arg3, ... , argN) something like this, so actually it's not a disadvantage because it is giving us a hint that we should refactor our code since, this class is dependent on so many resources

Circular Dependency
- Use @Lazy annotation on top of @Autowired, so it will not create the object at the start, so one of the class can be created at the start, this breaks circular dependency

- Suppose there are two classes, Order and Invoice, so in Invoice class, we can create a variable of order type without @Autowired or constructor, now when order class is invoked, it can create an object of type invoice without any problem, once order is created we can use @PostConstruct and set "this" to Invoice class

Unsatisfied Dependency problem
- Suppose we have a class Invoice, and we there's a dependency of Order order, now Order is a interface, so while initialization, which concrete implementation of Order to choose, for this you can use @Primary annotation of one of the concrete classes, Another approach is to using @Qualifier annotation and give a name, so you can use the same @Qualifier annotation while autowiring

+------------------+
|    BEAN SCOPE    |
+------------------+

@Scope(singleton)
Only one object is created per IOC, this object will be eager by default

@Scope(prototype)
Every time when it is called, a new object will be created

@Scope(request)
New object will only be created per HTTP call

Now, understand a scenario, what if a prototype class tries to create a scope request bean, so it will not be created until it is required because both are lazy in nature

But, what if a singleton bean tries at startup? It will give us "Failed to start the application" because @Singleton wants all dependencies at start, and the other class has request scope, so it is lazy by default.

To make it work we have to use a setting in @Scope(value="request", proxyMode=ScopedProxyMode.TARGET_CLASS), so at startup, it will create a dummy object and give it to the singleton class, and when a real HTTP request will come, it will replace it with the real object

@Scope(session)
It will create a new bean for every new session, obviously it is used in systems where session is maintained, so the bean will get destroyed in the /logout api, where session gets closed

@Scope(application)
If we want to maintain a single bean copy in multiple IOC containers in a huge application, then we can use this

Someday we might think that if we use @Qualifier then we are hardcoding which bean is required

so for this what we can do is,
class User:
    Order order

now we know that order is a interface so we can create two separate objects, one with qualifier of onlineOrder and another with offlineOrder, according to situation demand, we can then assign which one we want

another approach is not to do @Component on top of concrete classes and interfaces, instead create a configuration file and take value from application.properties, and in this configuration file by using @Bean return the required instance to the IOC container

Let's see another scenario, suppose we want to create a bean based on a key in application properties

how to do this?
we can use an annotation @ConditionalOnProperty(prefix, value, havingValue, matchIfMissing)

prefix.value = x
x will match with havingValue to take the decision of whether to create the bean or not

matchIfMissing means, if this key is not present in application.properties then should the bean get created or not?

Also, whenever you are using @ConditionalOnProperty you should make @Autowired(required=false)

because if @Autowired is enabled + you did config not to create that bean, then definitely it will lead to error
